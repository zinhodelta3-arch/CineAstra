# Movimentos e reserva de estoque — tarefa 26

API autenticada ADMIN/FORNECEDOR: `GET /api/inventory/inputs/:id`, `GET /api/inventory/equipment/:id`, `GET/POST /api/inventory/movements` e `GET /api/inventory/alerts?localId=...`. FORNECEDOR só lê/move itens próprios com vínculo operacional ativo; ADMIN pode corrigir itens históricos. `POST /movements` recebe exatamente um de `inputId` ou `equipmentId`, `tipo`, `quantidade` inteira não zero e `motivo` quando o tipo é AJUSTE, PERDA ou DEVOLUCAO. ENTRADA/DEVOLUCAO têm sinal positivo; SAIDA/PERDA negativo; AJUSTE aceita ambos. Saldo e histórico são gravados na mesma transação, sem saldo negativo. Saída manual só usa a parte disponível, sem consumir reserva de pedido.

Migration `20261009_10_inventory_reservations.sql` acrescenta `insumos.quantidade_reservada` com CHECK `0 <= reservado <= quantidade`, cria `estoque_reservas` única por pedido/insumo e associa movimentos de consumo/compensação à reserva. `quantidade` continua saldo físico; `disponivel = quantidade - quantidade_reservada`. IDs BIGINT permanecem strings. A migration foi preparada, não aplicada.

O serviço interno compartilha a transação/conexão do futuro checkout: `reserve(c,{orderId,localId,lines})` agrega insumos individuais e todos os componentes de cada combo, bloqueia pedido, combos por ID e insumos por ID crescente e reserva apenas se houver disponibilidade integral. Retry idêntico de reserva ATIVA é idempotente. `transition(c,{orderId,actorId,action})` usa CONSUMIR para baixar físico e reservado com SAIDA histórica, LIBERAR para devolver disponibilidade sem movimento físico e COMPENSAR para repor físico com DEVOLUCAO histórica. Cada transição é idempotente no próprio estado; estado incompatível retorna 409. O chamador deve criar pedido e itens, reservar, alterar status e confirmar/rollback na **mesma transação**. Não há endpoint público de reserva nem compra simulada nesta tarefa.

`GET /alerts` expõe insumos cuja disponibilidade está no mínimo ou abaixo dele. Isso fornece alerta operacional, mas não garante reposição antes de zero em alta demanda nem cria pedido não planejado; RF43/RN15 continuam parciais até solicitação/logística e interface. `backend/tests/inventory.test.js` cobre sinal, item único, acesso alheio, último item concorrente, combo completo, rollback parcial e compensação. Cenário MySQL opt-in em `backend/tests/integration/identity.mysql.test.js` cobre concorrência/reserva/rollback. Sem `TEST_DB_*` e schema `_test` vazio, SQL/locks reais permanecem pendentes.
