
CINEASTRA - PROMPTS DE AGENTES DE IA PARA IMPLEMENTAÇÃO DO BACKEND
=================================================================

OBJETIVO
--------
Este arquivo define uma sequência operacional de prompts para agentes de IA
implementarem o backend completo do CineAstra.

A sequência foi organizada para reduzir:
- código incompleto;
- duplicação;
- decisões arquiteturais conflitantes;
- regras de negócio espalhadas;
- vulnerabilidades;
- queries ineficientes;
- CRUDs artificiais;
- problemas de concorrência;
- inconsistências entre banco, documentação e código.

FONTE DE VERDADE
----------------
Considere como fontes principais:
1. schema MySQL/CineAstra fornecido pelo projeto;
2. documentação do levantamento de requisitos;
3. RF01-RF46;
4. RNF01-RNF36;
5. RN01-RN26;
6. Apêndice A - parâmetros configuráveis;
7. estrutura atual do repositório.

O banco e a documentação possuem precedência sobre suposições genéricas.

NÃO invente:
- tabelas;
- colunas;
- ENUMs;
- relacionamentos;
- regras de negócio;
- fluxos;
- integrações externas;
- credenciais;
- preços;
- parâmetros financeiros.

Caso haja conflito entre documentação, schema, migrations, seeds e código,
identifique o conflito e registre a decisão utilizada.

STACK OBRIGATÓRIA
-----------------
Node.js
Express
mysql2
dotenv
bcryptjs
jsonwebtoken
helmet
cors
multer

Quando necessário para cumprir os requisitos:
express-rate-limit
biblioteca de validação
sanitização apropriada
testes automatizados
ferramentas de observabilidade

ARQUITETURA-BASE
----------------
Adaptar à arquitetura existente, sem criar uma arquitetura paralela.

Preferência:

src/
  config/
  controllers/
  models/
  services/
  routes/
  middlewares/
  validators/
  utils/
  modules/
  uploads/
  app.js
  server.js

Princípio:

routes -> middlewares/validators -> controllers -> services -> models -> MySQL

Responsabilidades:

ROUTES
- definição de endpoints;
- encadeamento de middlewares;
- autenticação;
- autorização;
- rate limiting;
- validação;
- upload.

CONTROLLERS
- receber request;
- extrair dados;
- chamar services;
- responder HTTP;
- não conter regra de negócio complexa;
- não conter SQL de domínio.

SERVICES
- regras de negócio;
- transações;
- concorrência;
- cálculos;
- autorização contextual;
- orquestração de múltiplas tabelas;
- integração com serviços externos.

MODELS
- somente acesso ao banco;
- prepared statements;
- queries;
- transações quando a arquitetura escolhida centralizar isso no model;
- paginação;
- filtros;
- JOINs eficientes.

VALIDATORS
- formato;
- tipos;
- obrigatoriedade;
- limites;
- listas permitidas;
- sanitização.

MIDDLEWARES
- JWT;
- RBAC;
- rate limit;
- logs;
- segurança;
- tratamento global de erro;
- uploads quando aplicável.

PROMPT 02 - USUÁRIOS, AUTENTICAÇÃO, 2FA E PREFERÊNCIAS
=============================================================

Implemente o módulo de identidade do CineAstra.

TABELAS
-------

autenticacao_2fa

REQUISITOS
----------
RF01-RF07.

FUNÇÕES
-------
- cadastro de cliente;
- login de todos os perfis;
- recuperação de senha;
- redefinição;
- ativação/desativação de 2FA;
- validação de 2FA;
- perfil;
- atualização de dados;
- exclusão da conta quando aplicável;
- endereços;
- contatos;
- métodos de pagamento serão tratados no módulo financeiro;
- preferências.

REGRAS
------
- fornecedor, supervisor e colaborador não realizam cadastro público;
- contas desses perfis são criadas pela administração;
- senha com bcryptjs;
- nunca retornar hash;
- política de senha;
- confirmação de senha deve ser validada;
- CPF único e validado;
- e-mail único;
- ADMIN e SUPERVISOR precisam ter 2FA ativo;
- conta bloqueada/inativa não autentica;
- PENDENTE_VERIFICACAO respeita o fluxo definido pela aplicação.

SEGURANÇA
---------
- não permitir enumeração de contas em recuperação de senha;
- tokens de recuperação com expiração;
- token de recuperação de uso único;
- não colocar senha ou dados sensíveis nos logs;
- rate limit agressivo nos endpoints de autenticação;
- proteção contra brute force;
- resposta de login que não entregue informações desnecessárias;
- jamais confiar no role enviado pelo cliente.

2FA
---
Prepare abstração para:
- APP;
- SMS;
- EMAIL.

Não invente serviço externo real.

Para TOTP ou mecanismo equivalente, segredo nunca deve ser devolvido indevidamente.

LGPD
----
Estruture o módulo de modo a permitir:
- acesso aos dados;
- correção;
- exclusão;
- exportação;
- consentimentos;
- registro de base legal quando suportado pelo projeto.

IDADE
-----
Não trate autodeclaração como validação confiável quando o fluxo exigir validação.
Não invente um provedor de verificação de idade.
Crie interface/adaptador quando integração externa não estiver definida.

- CRUD de sessões;

- filtros por local/data/horário/filme;

REGRAS
------
1. Sala pertence a local.
2. Assento pertence a sala.
3. Sessão relaciona filme e sala.
4. Assento vendido em sessão deve pertencer à sala da sessão.
5. Sessões no mesmo local precisam respeitar intervalo mínimo de 1 hora.

7. Status válidos conforme banco.
8. Preço não negativo.
9. Sala precisa estar válida para receber sessão.
10. Filme precisa estar disponível para cinema quando utilizado em sessão.

ASSENTOS
--------
Consulta deve retornar apenas:
- assentos ativos;
- pertencentes à sala;
- não vendidos naquela sessão.

VENDAS
------
O mesmo assento não pode ser vendido duas vezes.

Use transação e locking quando houver risco de concorrência.

Não confie apenas na validação da aplicação.
Respeite a UNIQUE KEY do banco.

TABELAS

REQUISITOS

RF08.

IMPLEMENTE
----------
- aluguel;

REGRAS
------
Aluguel:
- data de início definida pelo fluxo;
- data de expiração calculada;

Compra:
- sem expiração quando definido como aquisição definitiva.
