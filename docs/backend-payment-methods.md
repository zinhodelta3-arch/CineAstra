# Tarefa 29 — métodos tokenizados e provider

Cinco operações em `/api/users/me/payment-methods`: GET da lista e de um ID, POST, PATCH do principal e DELETE lógico. Só CLIENTE autenticado acessa os próprios métodos. O corpo de criação aceita `type`, `setupReference` de um fluxo hospedado no gateway e `principal`; rejeita campos extras, incluindo PAN, CVV e token enviado pelo cliente. O provider retorna token opaco, marca e quatro dígitos; a API gera identificação mascarada e nunca devolve o token.

`paymentProvider` é injetado em `createApp`. O contrato exige `tokenize`, `create`, `consult`, `cancel`, `refund` e `verifyWebhook`. O adaptador padrão retorna 503 para todas essas chamadas. Ainda não há adaptador real configurado nem captura de cartão na API. O provider real deve garantir que `setupReference` pertence à sessão hospedada e ao usuário, e que o token emitido é utilizável para cobrança. Sem isso, cadastro de método permanece indisponível.

`20261009_13_payment_methods.sql` adiciona provider/token/ativo aos métodos, UNIQUE para token e principal ativo por dono, e `pagamento_intencoes` com UNIQUE por pagador e chave idempotente, obrigação XOR, método e valor decimal. Antes do ALTER é preciso auditar dados legados com mais de um principal por dono. Linhas legadas ficam com token NULL; podem aparecer na lista, mas não podem ser cobradas. DELETE apenas arquiva para preservar referências financeiras. `prepare` é serviço interno do checkout: na conexão transacional do pedido/cobrança valida pagador, propriedade do método, estado e valor; registra a intenção antes de qualquer chamada externa. Retentativas com a mesma chave devolvem o registro original; chave usada para outra obrigação falha 409. A tarefa 30 fará o despacho após commit e a conciliação por webhook, sem aprovação simulada.

Migration não aplicada. Para aceite, usar MySQL `_test` isolado e validar DDL, corrida de principal, UNIQUE/idempotência, FKs e rollback. Provider real, webhook, recorrência/mandato e estorno confirmado continuam pendentes nas tarefas 30–31/38–39. Frontend não alterado.
